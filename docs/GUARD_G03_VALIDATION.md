### AI and source safety

- AI-off deterministic guidance performs no source/provider access. AI-on requires a current provider plan digest and explicit request consent. Source disclosure additionally requires the exact finding path/base commit/source digest and a separately authorized redacted preview.
- The reader verifies current branch HEAD twice, immutable tree/blob identity, UTF-8/text/file mode and source SHA256. No entire repository or unrelated file is sent. Only at most 25 lines / 6,000 characters around the finding enter model context.
- Known credentials, tokens, private keys, connection strings, email addresses and opaque quoted values are redacted. Sensitive targets, dot directories, symlinks/submodules, binary files and unsafe paths are rejected. Redaction is conservative pattern-based minimization, not a claim to recognize every possible secret; the owner must review the preview.
- Untrusted comments/rules remain input data. The provider has no tools; output must match the strict advice/edit schema. Arbitrary paths, commands or extra fields are rejected. An edit must match exactly once in the original source; suppressions, dangerous API/process/network additions and invalid syntax are denied. Source around a diff must also pass disclosure checks. Neither model output nor repository test/install scripts execute on the host.
- One request, zero retries; 20-second provider deadline, bounded streaming output, 10,000-token conservative input reservation / 2,000 output-token cap. Prices must be explicitly configured in micro-USD per million tokens. Worst-case reservation ≤ $0.10/request; ≤ $0.50/project per rolling 24 hours, ≤ 20 AI requests/project/day, ≤ 1/actor/project/minute. A PostgreSQL project advisory lock serializes the budget across processes/scans. Failed/unknown attempts stay charged; idempotency never repeats them.
- Provenance includes finding/evidence version, source/base identity, actor/time/scope of consent, provider/model/prompt/data-policy versions, reserved budget and actual response ID/token usage. No provider errors, credentials or raw response bodies are logged/persisted.

Runtime settings (names only; no secret values provisioned/read by this task): `GUARD_G03_ENABLED`, `GUARD_G03_AI_ENABLED`, `GUARD_G03_PROVIDER=openai_responses`, `GUARD_G03_MODEL` (exact returned model identifier), `GUARD_G03_API_KEY_FILE`, `GUARD_G03_DATA_POLICY_APPROVED`, `GUARD_G03_DATA_POLICY_VERSION`, `GUARD_G03_INPUT_MICRO_USD_PER_MILLION`, `GUARD_G03_OUTPUT_MICRO_USD_PER_MILLION`, `GUARD_G03_GITHUB_WRITES_ENABLED`. Existing reviewed Guard product/app DB configuration is required. The key reference must be a private, non-symlink file outside dotenv; runtime credential loading follows the existing private-root controls. No owner configuration was enabled by this task.

OpenAI requests use `store:false`, strict structured output, no tools and no background mode. This does not certify zero retention or account-level sharing settings. Owner review of provider/account data controls is mandatory; no undocumented training opt-out flag is invented. See the official [Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create) and [data controls](https://developers.openai.com/api/docs/guides/your-data), checked 20 November 2026.

### PR and retest safety

Patch review and repository-write consent are independent. Publication verifies the current personal repository owner has admin/push permission and the existing App has contents/pull-request write permission; unsupported organization/delegated-owner cases fail closed. It mints a repository-scoped token through the existing App, creates only a new `wetscan/g03-<proposal>` ref, creates a commit with exactly the reviewed base parent/tree change, and opens a draft PR. No ref update, force push, default-branch push, OAuth flow, merge or deployment operation exists. Source/base are rechecked. Unknown write outcomes keep a consumed reservation; `pr-status` reconciles read-only and never republishes automatically. Manual recovery may be needed for an orphan branch with no PR.

Retest consent binds one relevant engine, repository, branch and changed commit. G03 calls the real G02 admission/scheduler/worker composition; G02 still enforces its deployment qualifications and branch/engine policy. A remediation PR branch must already be authorized by that policy, or the owner must retest the original authorized branch after a separately approved human merge. G03 never widens G02 policy or merges a PR.

`outcome=fixed` / `evidenceOutcome=verified_fixed` requires the exact reviewed patch's after-file bytes, original finding evidence, matching real scanner/image/spec/rules, complete relevant and source coverage, immutable revision identity and verified cleanup. The same rule/path/package is compared even if line numbers move. Missing coverage/errors → `inconclusive`; reproduced rule → `still_present`/`reproduced`; absent rule without sufficient proof → `not_verified`/`not_detected`. Secret rotation and false-positive/risk-acceptance triage cannot be verified by absence alone. Historical observations are appended. A checked moved branch/PR revision invalidates current verification and retains the earlier observation. The UI states that verification applies to the recorded commit and must be refreshed after changes.

Reports retain the original scan, coverage/exclusions, confidence, release evaluation, proposals/reviews/PR references, retest evidence, audit and limitations. They expire at the earlier of seven days and scan retention. Export is project-authorized, audited, no-store, attachment-only, HTML-escaped and CSP-sandboxed. The app has no DELETE/purge grant; physical retention purge remains operator-owned. No deployment enforcement is claimed.
