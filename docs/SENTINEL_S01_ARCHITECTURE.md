## Ownership and activation

The S00 contracts in `src/features/sentinel/platform-contracts.ts` are unchanged. Their PostgreSQL adapters live in `src/platform/`; Sentinel alone owns `sentinel.project_bindings` and `worker/sentinel/`. Shared tables live in `platform`. There is no Guard schema, Guard job enrollment or scanner invocation. Guard may later adopt the same transaction/job/outbox interfaces through separately reviewed adapters, roles and tests. Its existing scanner worker and ports remain unchanged.

The prototype, Demo Mode, Auth/Canvas/Guard implementations, navigation and shared routes are unchanged. No Next.js route or UI imports this platform runtime. Merely building or starting Next.js does not open a new platform pool, migrate or start a Sentinel worker. No telemetry, detection, incident, external notification, Ghost or Intelligence implementation is added.

`registerAuthorizedProject` calls the existing Sentinel/Canvas server authorizer before opening a database transaction. The binding records its authorized repository/actor identifiers, preserving `github-user-<id>:<workspace>` and `github-<repository id>` exactly. It is processing metadata, not a replacement repository registry or OAuth grant. Workspace rename remains an explicit future migration decision. Future endpoints must reauthorize every operation, including revocation/disable actions; possessing a scope DTO or setting a PostgreSQL session variable is **not authentication**. No user-facing enrollment or automatic revocation feed is wired in S01.

## Storage and transactions

`ApprovedPool` accepts purpose-specific, local-only configuration after validating an ignored approval record, exact target and plan hash. It checks database name/comment marker, login role, server version (17 or later) and non-superuser/non-bypass role on connection. It does not consume ambient connection URLs or PostgreSQL credentials. Local TCP uses no TLS; this configuration is restricted to approved loopback development targets.

`PlatformDatabase` implements the frozen transaction port. One checked-out client handles BEGIN, transaction-local module/mode/workspace/project variables, all caller work, and COMMIT or ROLLBACK. Opaque transaction handles expire on release and cannot be reused on another pool or scope. Failed rollback destroys the connection. Driver statement/query/connection timeouts bound waits. Project-bound operations reject Demo Mode.

App RLS requires live Sentinel module plus matching project/workspace session context. The trusted Sentinel worker SQL role has module-wide live Sentinel access, rather than per-project raw-SQL isolation; the scheduler selects registered bindings and job operations additionally enforce scopes and active bindings. Both roles are denied Guard/demo rows by forced RLS. The worker's SQL grants cannot change binding identity/enabled/hold fields. The migrator owns schema objects and has a read policy to perform occupied-database rollback checks, but the worker process never uses that role. Real conflicting-row isolation was verified on the separate acceptance database; development role/grant/active-policy checks were read-only. RLS supplements trusted server authorization; the application database role is not a client credential.

## Durable jobs and outbox

Enqueue locks the authorized active binding, enforces a 1,000 active-job project cap and uses a scoped unique idempotency key plus immutable-payload SHA-256. A repeated matching request returns its original receipt; conflicting reuse fails. Identifiers/reference fields are bounded; no executable job payload, source file or provider credential is stored.

Claim transactions lock a module-limit row, account for active leases across worker processes, and select due/expired work with `FOR UPDATE SKIP LOCKED`. The Sentinel module budget is two active leases. Each claim increments attempts, revision and a monotonic fence, and issues a fresh token. Heartbeat, complete and retry compare project/module/job/owner/token/revision and database-clock expiry. Expired or cancelled leases cannot settle. Attempt records survive process exit; reclaim closes the previous attempt. Retries use bounded exponential backoff with jitter, maximum five attempts, then a persisted failed state. No exactly-once side-effect guarantee is claimed: future handlers must honor cancellation and fence/idempotently commit their own effects.

Project disable locks the binding, cancels queued/leased work, invalidates revisions and closes attempt/outbox state in one transaction. Direct job cancellation is also durable. Workers stop claiming disabled bindings. The executor serializes heartbeats, aborts handlers on shutdown/timeout/lost lease and refuses stale settlement. The only installed handler is infrastructure maintenance; no customer code or scanner runs.

Outbox append and its durable job use the caller's transaction. Delivery ID and idempotency key must be stable across retries; conflicting content is refused. Attempt outcomes distinguish `not_configured`, `failed` and `accepted`; acceptance requires an evidence reference and completes the job atomically. S01 registers **no outbox/provider handler**, creates no notifications automatically and sends nothing. A future provider receipt must be genuinely verified before using the acceptance adapter; its existence cannot prove recipient delivery.

## Worker, health and limits

`npm run sentinel:worker` retains the separate Node command using only `wetscan_sentinel_worker`. `main.ts` performs credential hygiene/configuration, while `runtime.ts` verifies the exact migration ledger, pages registered projects in batches of 100, performs bounded retention and claims only `sentinel.maintenance`. It neither enrolls jobs nor imports Guard scanners. Known Auth/GitHub/provider credential environment entries and unused password-file paths are removed; this is process hygiene, not an OS sandbox.

`lifecycle.ts` provides one idempotent shutdown coordinator. SIGINT/SIGTERM and Windows SIGBREAK request cancellation; a child explicitly forked with an inherited Node IPC channel also accepts `{type:"sentinel.shutdown",version:1}` from its parent, and stops on parent disconnect. There is no HTTP shutdown route, token in committed files or network control listener. Repeated requests share cleanup. New claims stop, polling/heartbeat waits are aborted, and active executor operations receive the same cooperative cancellation signal. Cleanup enters even if a polling operation is pending: drain at most five seconds, close HTTP/idle sockets (remaining sockets after one second), record a stopped heartbeat only after draining against a verified ready schema, then close the pool. All cleanup shares a nine-second budget; failure is redacted and surfaced, never relabeled success. Deadline timers/listeners/IPC are released. No unconditional `process.exit()` is used for normal shutdown. Queue fencing, retry/cancellation and outbox SQL are unchanged.

The first Windows PTY shutdown failure remains in the acceptance history, including its forced termination and preserved stale heartbeat. New database-free probes reproduced missing SIGINT on the same PTY with bare Node, `tsx` and npm; ordinary input bytes were delivered. This establishes an unreliable terminal interrupt path without implicating a database operation; it does not identify the specific Windows console internals. For explicit local lifecycle testing, `npm run sentinel:worker:smoke` now forks direct worker children with private IPC, a 180-second overall watchdog and ten-second idle shutdown deadline. It requires a separate exact-target runtime approval plus the existing migration-only observer approval via `SENTINEL_SMOKE_OBSERVER_APPROVAL_FILE`; that observer only reads and cannot cause a migration through this harness. It preserves historical heartbeat fields and never enqueues jobs or events. Failure stops the sequence and cleans up only its owned child.

The single authorized real retest passed on the approved development target: shutdowns **22 ms / 20 ms**, both exits 0, both stopped heartbeat rows persisted, no worker sessions/listeners/processes remained. Restart obtained a new worker ID and a fresh advancing heartbeat while preserving the old stale row. The separate runtime-only retest approval is closed; normal dev approval remains migration-only. This verifies Windows private-parent IPC lifecycle, not Linux signals or Ctrl+C in another terminal.

The worker exposes loopback-only `GET http://127.0.0.1:3112/health` and a separate health CLI. Database connectivity, schema readiness, worker heartbeat freshness (30 seconds), queue counts/lag/expired leases/failures and pending outbox are separate fields. Provider is `not_configured`; telemetry is `not_implemented`. Missing config returns `not_configured`; database errors do not become healthy empty results. These are infrastructure checks, not proof that an application is monitored. There is no shared routing change or public endpoint.

The owner accepted these development budgets during H01. A hard worker RSS/CPU boundary needs an owner-selected process supervisor/container before any heavier future workload; S01 installs only trusted maintenance. The real idle sample used one worker-role DB connection and 37,580,800 bytes working set; this is not a peak or hard RSS-limit measurement. Guard budgets remain owned by Guard, with no shared scanner process or credentials. Adding more processes must respect the 40-connection database budget. Shared primitives are reusable; Guard adoption is not operationally verified by this packet.

Retention skips held or not-due projects, active jobs and pending outbox work. It cascades only owned attempt records after terminal records expire. Disabled bindings are still visited for retention. Stale module heartbeat metadata also expires after the configured retention period, at most 100 records per poll; fresh worker records are preserved. No event/evidence/incident retention is implemented: later packets must define their own retention and holds. The approved migration down path refuses any runtime records instead of deleting them.
