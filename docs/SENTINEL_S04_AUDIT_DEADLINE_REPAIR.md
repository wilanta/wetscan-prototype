# S04 minimal audit deadline repair

Offline repair only. Overall `IMPLEMENTED_PENDING_ACCEPTANCE` and authentication `ACCEPTED_OFFLINE_WITH_DOCUMENTED_RESIDUAL_RISKS` are unchanged. Historical manifests, failed receipts and the previous infrastructure rebaseline remain immutable.

The existing launcher fixes one absolute deadline immediately before coordinator process startup. Its monotonic wait subtracts startup and journaling time from the existing 210 seconds. It supplies that deadline to the existing coordinator; missing, malformed or excessive deadline evidence fails closed in a recorded stage. The coordinator uses both elapsed monotonic time and wall time, choosing the smaller remaining budget so clock rollback cannot extend execution.

Before admission, and again immediately before launching the audit runner, at least **170 seconds** must remain: the existing **150-second audit-process cap** (120-second audit plus 30 seconds for startup/offline checks) and **20 seconds for cleanup**. The cleanup reserve comes from the existing 10-second coordinator cleanup command, up to 5 seconds for native process termination and the launcher's shared 5-second owned-process wait. Approval closure and lock handling are inside the cleanup command; the audit's watchdog handshake remains within its independent 120-second phase deadline. At exactly 170 seconds admission is allowed; one millisecond less fails. Completion must still precede the outer deadline; spending the entire reserve is a timeout, never PASS.

The same deadline is forwarded to the existing PowerShell audit runner. After its own offline checks and before creating output or approval, it requires 140 seconds remaining (120-second audit plus the same cleanup reserve). It checks again after path/ACL checks, ensuring the new approval's 120-second expiry is at least 20 seconds before the shared outer deadline. This closes the handoff gap if inner preflight or startup is unexpectedly slow. No database, authentication, authorization, read-only transaction, fixed SQL, preservation or closure requirement is removed. The TypeScript database audit core is unchanged.

Existing Docker readiness returns on its first valid result. Only transient read-only probes may be polled, bounded by 120 seconds total and 20 seconds each. The coordinator reduces that existing observation window to the time available before the audit and cleanup reserve; polling cannot waste time after admission becomes impossible. Identity or integrity mismatches fail immediately. A prolonged readiness observation can cause admission to fail; it cannot obtain more time. The isolated replacement container, volume, image and loopback endpoint remain unchanged.

The new phase-specific package must reconcile only the launcher, coordinator, audit-runner handoff and explicit source-pin reconciliation changes. It must retain the six authentication bindings, required-absent archived session, four dotenv bindings, original database baselines, containment evidence and isolated-clone evidence. Prior manifests and failure receipts remain historical evidence. A fresh single-use owner grant is required before any live execution; no consumed grant can be reused.
