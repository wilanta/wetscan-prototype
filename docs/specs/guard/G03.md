# WetScan Guard — G03 AI Remediation & Verified Retest

## Objective

Implement complete AI-assisted remediation, safe patch proposal, targeted retesting and durable evidence reports.

Repository: `wilanta/wetscan-prototype`

Scope:

- GRD-017 AI Provider and Privacy
- GRD-018 Safe Patch and Targeted Retest
- GRD-022 Durable Reports and Retention

## Mandatory preparation

Read all existing Guard architecture, findings, evidence, release, AI and retest contracts, G01/G02 handoffs and current Git state.

Use a dedicated feature branch/worktree such as `feat/guard-g03-remediation`.

Preserve Sentinel and all existing authentication, scanner and demo functionality.

## 1. AI provider architecture

Implement a provider-agnostic AI orchestration layer.

Requirements:

- Configurable LLM provider and model.
- Server-side credential management.
- Explicit AI opt-in.
- Redacted input context.
- Structured, validated output.
- Token/cost and request budgets.
- Timeouts and bounded retries.
- Rate limits.
- Provider error handling.
- Model/prompt version provenance.
- Audit of remediation requests.
- No source/secrets disclosure without explicit permission.
- No use of user repository content for model training through undocumented settings.
- Deterministic fallback when AI is unavailable.

Treat repository source and scanner output as untrusted input. Prevent prompt-injection content from triggering tools or actions.

Never claim a model is configured or has produced real results unless a real call succeeds.

## 2. AI remediation analysis

For each real Guard finding, support:

- Vulnerability explanation.
- Root-cause analysis.
- Affected file/location.
- Severity and confidence context.
- Suggested code change.
- Security consequences.
- Compatibility risks.
- Expected verification method.
- Alternative remediation where appropriate.

Persist sanitized, versioned remediation proposals.

AI output is advice, not verified security evidence.

## 3. Patch proposal engine

Implement safe patch proposal generation tied to:

- Authorized repository.
- Exact base commit.
- Finding ID and evidence version.
- Allowed file paths.
- Patch diff.
- Expected post-change behavior.

Requirements:

- Minimal diff.
- Path allowlist and sensitive-file exclusions.
- Reject binary and unsafe patch targets.
- Reject stale commit.
- Do not silently rewrite unrelated files.
- Verify patch applies cleanly.
- Validate syntax and relevant tests.
- Preserve existing repository content.
- Prevent malicious model output from executing arbitrary commands.

Provide a human review UI showing the proposed changes.

Do not auto-merge changes.

## 4. GitHub Pull Request integration

Implement the backend and approval workflow for creating a remediation PR.

A PR may be created only after:

- Current GitHub write permission is verified.
- The repository owner explicitly authorizes the target and operation.
- The diff is reviewed.
- The base commit and branch are verified.
- Sensitive data checks pass.

Use a dedicated remediation branch.

Support PR creation, link storage, status tracking and audit.

Do not force-push, modify protected branches directly or auto-merge.

If GitHub write permissions are not yet available, complete the proposal/review implementation and report PR creation as blocked.

## 5. Targeted retest

After a patch is applied to an authorized revision:

- Run the relevant scanner again.
- Preserve before/after commit identities.
- Compare the specific original finding.
- Store actual scanner evidence.
- Distinguish reproduced, not_detected and verified_fixed.
- Treat missing coverage/errors as inconclusive.
- Do not mark a generic clean scan as proof of a fix.
- Invalidate stale verification when the target commit changes.

Implement real lifecycle status in Guard UI.

## 6. Durable reports

Implement project-scoped server-generated reports with:

- Scan metadata.
- Scanner coverage and exclusions.
- Findings and confidence.
- AI proposals and review status.
- Patch references.
- Retest evidence.
- Release evaluation.
- Audit trail.
- Limitations and provenance.

Support JSON and HTML, plus PDF only if a suitable existing rendering dependency is available or separately reviewed.

Ensure:

- Access controls and RLS.
- Expiration/retention.
- Audit of downloads.
- HTML/XSS protection.
- Secret redaction.
- No demo data inside live reports.
- No claim of deployment enforcement before G04.

## 7. Validation

Run:

- AI-off fallback.
- Real provider acceptance when configured/approved.
- Prompt-injection and output validation.
- Provider timeout/error.
- Cost/rate budgets.
- Malicious/invalid patch denial.
- Human approval gates.
- GitHub permission denial.
- Safe PR behavior where approved.
- Vulnerable/fixed retest.
- False-positive and inconclusive outcomes.
- Report authorization, retention and XSS tests.
- Full unit, lint, typecheck, build and browser regressions.

No fake LLM or real GitHub acceptance claims.

Create:

`docs/GUARD_G03_VALIDATION.md`
`docs/agent-handoffs/HANDOFF_GUARD_G03.md`

Include actual implementation, model/provider configuration status, diff safety, retest evidence, remaining approval gates, Git state, full changed-file manifest and complete copy-ready G04 continuation prompt.

No agent name in the handoff filename.

Do not commit/push/PR the Guard implementation branch without separate permission.

## Final output

Report all implemented features, actual AI/patch/retest acceptance, tests, blockers, handoff and remaining actions.

Do not begin G04 automatically.
