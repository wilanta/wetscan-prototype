# WetScan Guard — G05 Secure DAST, Trust & Integrity Engine

## Objective

Implement actual, consent-based staging DAST, authenticated API security testing, Canvas Trust plan consumption and Integrity verification.

Repository: `wilanta/wetscan-prototype`

Scope:
- GRD-011 Scoped Staging DAST
- GRD-012 Authenticated DAST Accounts
- GRD-014 Canvas Trust Plans
- GRD-015 Canvas Workflow Import
- GRD-016 Live Integrity Runner

## 1. Initial audit

Read existing Guard security, DAST scope, Integrity contracts and test implementations.

Read current G01–G04 handoffs and the Canvas Trust/Workflow contracts.

Use an isolated Guard branch/worktree Use an isolated branch/worktree such as `feat/guard-g04-cicd`..

Preserve all existing modules, current Auth and Sentinel development.

Do not treat fixture-only Integrity results as live evidence.

## 2. Safe DAST engine

Implement a working DAST adapter for explicitly authorized staging applications.

Requirements:

- Exact target origin.
- Allowed paths and methods.
- Owner consent and expiry.
- Staging-only policy.
- Request/concurrency/rate limits.
- Bounded response sizes and redirects.
- Enforcing DNS and IP restrictions.
- DNS rebinding protection.
- Cloud metadata/internal-network denial.
- Safe cancellation.
- Execution audit.
- Redacted request/response evidence.
- No unsolicited third-party requests.

Do not rely only on URL string validation.

The actual outbound network path must enforce the approved destination and deny forbidden addresses.

Start with bounded, non-destructive security checks on approved synthetic endpoints.

Do not run broad active attacks, unrestricted fuzzing, or tests against live production.

GET requests must still be treated as potentially state-changing unless the specific target has been reviewed.

## 3. Authenticated API testing

Implement controlled test-account support:

- Synthetic account references.
- Explicit role/context assignment.
- Short-lived secrets.
- Encrypted credential handling.
- Session expiration and cleanup.
- No real-user account takeover tests.
- No real customer data.
- Per-target consent.
- Request/response sanitation.

Support approved authorization checks such as expected 401/403 versus actual responses.

Do not store raw cookies, session tokens or sensitive bodies in findings.

## 4. Canvas Trust integration

Consume explicitly confirmed Trust plans through the approved Canvas interface.

Never infer permission policies solely from the graph.

Verify:

- Authorized project/workspace.
- Confirmed policy version.
- Target commit or graph revision.
- Expected actor/resource permissions.
- Test expiry and consent.
- No cross-project plan reuse.

Keep expected policy separate from observed test results.

## 5. Workflow Integrity engine

Implement actual verification of the five existing invariant families:

1. Ownership.
2. Workflow bypass.
3. State transition.
4. Replay.
5. Unauthorized modification.

Use safe pre-approved staging test resources.

Capture:

- Expected behavior.
- Observed behavior.
- Test operation.
- Scoped evidence.
- Redacted response summary.
- Verified revision/policy identity.
- Start/end timestamps.
- Cleanup outcome.

Never modify actual customer resources or production data.

Implement explicit cleanup of synthetic resources.

## 6. Independent verification

Separate:

- Test plan defined.
- Test authorized.
- Test executed.
- Observation recorded.
- Result evaluated.
- Cleanup verified.

A passing policy definition is not evidence that the target application enforces it.

If the staging target is unavailable, report NOT_EXECUTED instead of PASS.

## 7. UI integration

Extend the existing Guard workbench:

- DAST scope confirmation.
- Target/permission preview.
- Test-account configuration status.
- Test execution status.
- Trust verification results.
- Integrity workflow results.
- Evidence inspection.
- Failed/inconclusive states.
- Targeted retest.

Preserve Demo/Live isolation.

## 8. Required tests

Test:

- No consent.
- Expired consent.
- Forbidden target.
- Private/metadata IP denial.
- Redirect and DNS rebinding.
- Request cap and timeout.
- Revoked test account.
- Wrong role/workspace.
- Unauthorized state transition.
- Replay test.
- Cleanup and recovery.
- Stale policy/revision.
- Partial execution.
- Redaction and evidence storage.

Run unit, typecheck, lint, build and browser regressions.

Real staged HTTP acceptance requires an owner-approved staging application with synthetic data and an enforcing egress environment.

If those conditions are absent, complete the code and safe local fixtures but keep live execution blocked.

## Restrictions

- No production or third-party scanning.
- No disabling egress restrictions.
- No credential leakage.
- No modification of real customer data.
- No automatic staging mutation without specific approval.
- No changing Sentinel, Canvas ownership or shared auth contracts.
- No automatic commit, push, merge or deploy.

## Completion criteria

Report each engine as LIVE_VERIFIED only when it has executed against an explicitly authorized target with actual request/response evidence and cleanup verification.

Do not begin G06 automatically.
