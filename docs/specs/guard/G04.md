# WetScan Guard — G04 CI/CD, Security Gate & Deployment Enforcement

## Objective

Implement actual CI/CD security checks and enforceable release gates for WetScan Guard.

Repository: `wilanta/wetscan-prototype`

Scope:

- GRD-019 Actual CI Release Enforcement
- GRD-023 Schedules and Webhooks
- GitHub integration
- Vercel deployment verification and release gating
- Provider adapter architecture for future platforms

## Mandatory baseline

Inspect merged G01–G03 implementation and handoffs, existing Guard release logic, GitHub App authorization, project selection, queue, reports and current deployment configuration.

Use an isolated branch/worktree such as `feat/guard-g04-cicd`.

Do not access or alter the Sentinel development working directory.

Preserve existing Auth, Canvas and Demo Mode.

## 1. GitHub webhook ingestion

Implement a secure endpoint for GitHub App events.

Support relevant:
- push
- pull_request
- installation/repository permission changes
- applicable check rerun requests

Requirements:

- Signature verification.
- Event type allowlist.
- Delivery ID idempotency.
- Replay protection.
- Payload limits.
- Repository installation authorization.
- Current repository access validation.
- Exact commit SHA.
- Branch/ref validation.
- Ordered status handling.
- Safe retries.
- Durable audit.
- Bounded webhook processing.

A webhook must not execute scanners directly in an HTTP handler.

Only enqueue authorized jobs through the Guard worker.

## 2. Automated scan policies

Support per-project policy configuration:

- Selected branches.
- PR scanning.
- Commit scanning.
- Manual scans.
- Required engines.
- Blocking severities.
- Confidence thresholds.
- Coverage requirements.
- Failure behavior.
- Optional scheduled scans.
- Policy version and audit history.

Implement secure defaults.

High/Critical can be configured to block, Medium to warn and Low to pass, but make this a configurable policy rather than a universal vulnerability guarantee.

Ensure scan evaluations always reference the exact commit being checked.

## 3. GitHub Checks integration

Implement real GitHub Checks publishing through the existing GitHub App.

Before enabling writes, verify the current GitHub App has the required permissions.

Implement:

- queued/in_progress/completed check states.
- PASS/WARN/BLOCK/INCOMPLETE mapping.
- Exact commit SHA.
- Project/repository installation identity.
- Scanner coverage.
- Finding summary.
- Links to authorized Guard evidence.
- Retry/rerun.
- Stale check rejection.
- No false successful conclusion when required checks are missing.

GitHub Checks API write access is restricted to GitHub Apps. Do not use a personal token as an unauthorized substitute.

A published check is not automatically an enforced branch rule.

Document and verify separately whether the target repository has required-check protection enabled.

Never alter GitHub repository rules without explicit owner approval.

## 4. Vercel integration

Implement a Vercel provider adapter.

Required:

- Authorized Vercel project mapping.
- Deployment ID.
- Repository and commit mapping.
- Environment identification.
- Revision verification.
- Deployment state retrieval.
- Independent evidence of provider state.
- Stale/partial/unavailable status.
- Audit of provider calls.
- Read-only verification by default.

Research the provider's current official APIs, plan requirements and available deployment-control mechanisms.

Use actual Vercel Deployment Checks where supported and authorized.

Prove the difference between:
1. Preventing a GitHub PR merge.
2. Preventing production promotion.
3. Preventing deployment creation or build execution.

Never claim that Vercel deployment creation was blocked merely because a Guard check failed.

If Vercel cannot enforce a requested behavior under the available plan/configuration, report unsupported rather than simulating enforcement.

## 5. Real deployment gate

Implement a complete decision flow:

Authorized commit
→ Guard scan
→ Persisted findings
→ Security policy evaluation
→ Provider check submission
→ Independent provider-state verification.

Test at least:

- PASS commit.
- WARN commit.
- BLOCK commit.
- INCOMPLETE scan.
- Wrong commit.
- Stale deployment.
- Missing permission.
- Provider outage.
- Replayed webhook.
- Concurrent commit updates.
- Re-evaluation after remediation.

No deployment-changing action without explicit approval.

## 6. Schedules

Implement bounded scheduled scans with:

- Explicit enabled state.
- Project/branch selection.
- Next execution time.
- Current repository authorization.
- Idempotent enqueue.
- Rate/usage limits.
- Retry and audit.
- Disable/revocation behavior.
- No overlapping scan storms.

Do not introduce an additional scheduler if the existing platform provides a compatible scheduler.

## 7. UI integration

Update existing Guard pages with:

- Security Policies.
- CI/CD integrations.
- Deployment Gates.
- Check history.
- Deployment verification.
- Scan triggers and schedules.
- Fail/incomplete explanations.
- Actual enforcement status.

Keep:
`decision != enforced`

until actual provider enforcement evidence exists.

Preserve original navigation/design and Demo Mode.

## 8. Provider extensibility

Define an interface suitable for future Netlify, Railway, GCP, AWS, Azure and VPS-based workflows.

Do not claim every provider is operational merely because an interface exists.

Vercel is the first acceptance target. Each additional provider requires separate credentials, permissions, environment and actual positive/negative tests.

## 9. Validation

Implement unit, integration and E2E tests for webhook security, scheduling, commit binding, queue dedupe, check publication, required-check behavior, provider failures and deployment gating.

Run the complete regression suite.

A real protected-branch or Vercel production-promotion test requires explicit authorization and a controlled test repository/project.

Do not manipulate the user's real production deployment to demonstrate a block.

## 10. Handoff

Create:

`docs/GUARD_G04_ARCHITECTURE.md`
`docs/GUARD_G04_VALIDATION.md`
`docs/agent-handoffs/HANDOFF_GUARD_G04.md`

Document:
- Actual provider integrations.
- GitHub App permissions.
- Policy and event contracts.
- Check/run/deployment identifiers without secrets.
- Actual enforcement evidence.
- Unsupported providers.
- Approval gates.
- Full changed-file manifest.
- Git branch/PR status.
- Complete copy-ready G05 continuation prompt.

## Restrictions

No silent repository-rule changes, provider credential additions, production deployments, automatic merge, or broad shared-auth modifications.

No commit/push/PR publication without separate approval.

Stop at external provider approval gates and report the exact action the owner must perform.

## Completion criteria

G04 is complete only for providers and workflows with actual enforcement evidence.

A local policy result, mocked GitHub check, or successful Vercel preview build does not establish production release enforcement.

Do not start G05 automatically.
